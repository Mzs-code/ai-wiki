## 一、技术基本要求(概念题)

### 1. LLM 的本质是什么?

- Q1 既然只是接龙,为什么会推理写代码?

<details><summary>参考答案</summary>

- 本质是"文字接龙机":基于前文预测下一个 token 的概率模型,逐个生成拼成回答。
- 类比:像规模超大的输入法联想/自动补全——只是大到能接出整段推理和代码。
- 知识来自训练:把海量语料压缩进参数,学到的是统计规律,不是事实数据库——回答是"凭印象生成"而非查资料,所以会一本正经地胡说。
- 合格关键词:**下一个 token 的概率预测**、**语料压缩进参数**。讲不到这两点是道听途说。
- **追问 · 期望**:规模效应+语料含推理模式+思维链

</details>

### 2. 一次 LLM 交互会发生什么?

- Q1 如何形成连续对话?
- Q2 LLM 有记忆/状态吗?
- Q3 上下文限制是什么?
- Q4 Lost in the Middle?

<details><summary>参考答案</summary>

- 流程:客户端组装提示词(system+工具定义+历史+本轮输入)→ 切 token 整段读入 → 自回归逐 token 生成 → 按输入/输出 token 分别计费。
- **模型无状态无记忆**:连续对话是客户端每轮把完整历史重发一遍,"记忆"是应用层拼出来的假象;ChatGPT 的记忆功能也是应用层存要点再注入。
- 类比:模型像每次都"失忆"的考生,客户端每轮把之前的卷子连题带答重新摊给它看,它才显得"记得"。
- 推论:对话越长每轮越贵——会话管理(截断/总结/缓存)管的就是这件事。
- 上下文窗口=单次请求 token 上限;窗口大不等于免费,长上下文每轮都计费。
- **Lost in the Middle**:超长上下文中,模型对开头结尾利用最好,中间内容易被忽略——关键信息放两端,资料先摘要再注入,不是塞得越多越好。
- 🚩 **扣分项(错误回答)**:认为"模型记住了我们聊过的内容";没听过 Lost in the Middle。

</details>

### 3. Claude Code 的系统提示词看过吗?

- Q1 CLI 与 Agent SDK 的系统提示词区别?
- Q2 plan mode 本质?
- Q3 auto mode 实现原理?

<details><summary>参考答案</summary>

- 先验证是否亲手看过:本地代理抓请求、社区提取版仓库、SDK 文档,任一具体路径即可。内容大致含:身份与语气约束、工具使用规则、安全红线、git 规范,并动态拼接环境信息与 CLAUDE.md。
- CLI vs SDK:CLI 自带完整产品化提示词;Agent SDK 默认接近空白,交付的是 harness 本体(循环/工具/权限/hooks),提示词留给开发者写——"成品"与"毛坯"的分界。
- **plan mode 本质=上下文注入 + 权限限制双层**(不是换了个"更会规划"的模型,能力来自 harness 工程):
  - 上下文层:进入后会修改发给 LLM 的内容——注入指令告知模型"当前处于 plan mode,只许研究/制定计划、不许改动,完成后调用 ExitPlanMode 工具呈现方案",并把 ExitPlanMode 工具挂给模型;
  - 权限层:harness 在工具执行前强制拦截写操作与有副作用命令、只放行只读工具(由 Claude Code 强制,不靠模型自觉);方案经用户批准后切到其他权限模式才放开写权限。
  - 两层缺一不可:光有提示词模型可能仍试图写(概率性),光有权限模型不知道该规划、会反复撞墙。
- **auto mode(自动批准,research preview)本质=独立分类器 LLM 做事前安全审查**,不是"放宽门卫的白名单",也不是"全放行";有门槛(Claude Code v2.1.83+、特定模型、账户/管理员开通)。〔下文涉及的模型名(Sonnet 4.6)、版本号(v2.1.83)截至 2026-06,会迭代,以官方 permission-modes 文档为准〕主模型照常发起工具调用,但**不是每个动作都过审查**,而是分三层决策:

  ```
          模型发起一次工具调用
                  │
                  ▼
     ┌────────────────────────────────────┐
     │ Tier 1  命中 allow / deny 规则?      │── 是 ─▶ 直接放行 / 拒绝
     │         (按 deny→ask→allow 顺序)     │        受保护路径写入除外
     └────────────────────────────────────┘
                  │ 否
                  ▼
     ┌────────────────────────────────────┐
     │ Tier 2  只读 / 工作目录内文件编辑?    │── 是 ─▶ 直接放行
     │         (受保护路径除外)             │
     └────────────────────────────────────┘
                  │ 否 (Shell、网络请求、项目外、外部工具…)
                  ▼
     ┌────────────────────────────────────┐
     │ Tier 3  交给 classifier(Sonnet 4.6)│
     │   ① 单 token yes/no 粗筛,偏向拦截    │
     │   ② 仅存疑动作再跑 CoT 推理复核       │
     └────────────────────────────────────┘
                  │
            ┌─────┴─────┐
          放行        拦截 ─▶ 把原因回灌主模型,它换更安全的方案
                            (explicit ask 规则在任何情况下仍强制询问)
  ```

  - **classifier 的三个易错点**(这题能拉开差距的地方):① 它**是 LLM 不是传统小分类器**——跑在固定的 Sonnet 4.6 上,与你 `/model` 选的主模型解耦、按 token 计费,术语叫 "LLM-as-classifier";② 它**故意"reasoning-blind"**——只看 user 消息 + 工具调用命令,剥掉主模型自己的话和工具输出,防止 agent 用"说服性理由"把审查员带偏(核心 prompt-injection 防线);③ 进入 auto 会**丢弃宽泛 allow 规则**(`Bash(*)`、`Bash(python*)`、包管理 run、`Agent` 等),离开时恢复。
  - auto 还会**促使主模型少停下来问澄清问题**——所以不能说"模型不知情、提示词不变"。
  - 进阶:PreToolUse hook 可做更细粒度审批,但**不能绕过已有 deny/ask 规则**(只能加严)。
- **完整 6 档权限谱系**(把这三者笼统叫"自动模式"是扣分项):

  | 模式 | 不询问即可执行 | 仍会拦/仍会问 |
  | --- | --- | --- |
  | `default` | 只读 | 其他工具首次用要批;**已存规则不再重复问** |
  | `acceptEdits` | 读 + 工作目录内文件编辑 + `mkdir/touch/rm/mv/cp/sed` 等 | 目录外、受保护路径、其他 Bash |
  | `plan` | 只读 | 任何写操作 |
  | `auto` | "全部 + 后台分类器安全检查" | Tier 3 高风险动作交 classifier;explicit ask 仍问 |
  | `dontAsk` | 仅预批准工具 + 只读 | 其余一律自动拒绝(ask 也拒) |
  | `bypassPermissions` | 几乎全部 | **explicit ask 规则 + `rm -rf /`、`rm -rf ~` 熔断仍提示** |

- **务必区分两种"问你"**(高频混淆点,能分清是加分信号):① 权限询问——门卫把工具调用拦下问你批不批,由上面的模式与规则决定;② 模型主动的选择题——模型觉得需求有歧义、请你拍板方向,与权限模式无关,**即便开了 bypassPermissions 全放行,模型照样会问**。注意 auto 模式本身会压低主模型主动问澄清的频率,所以这两类"问你"在 auto 下都会变少。
- 🚩 **扣分项(错误回答)**:把 plan mode 说成"换了个模型";把 auto 当成"简单白名单放宽""全放行"或"AI 自己决定要不要问你";把 classifier 当成传统小分类器(它是 Sonnet 4.6 这个 LLM);以为"每个动作都过 classifier"(前两层已直接处理大部分);把"门卫问权限"和"模型问你拿主意"混为一谈。

</details>

### 4. 怎么理解 ReAct / agent 循环?

- Q1 思考→行动→观察各步做什么?
- Q2 为什么 agent 这两年被广泛认同?

<details><summary>参考答案</summary>

- **核心是一个循环**,模型不是一次把话答完,而是"想一步、做一步、看结果、再想",像带一个实习生干活:

  ```
          ┌──────────────────────────────────────────┐
          │                                          │
          ▼                                          │
     思考(Thought)──▶ 行动(Act)──▶ 观察(Observe)──┘
     想下一步该          调用工具去         把结果(含报错)
     做什么、为什么       执行              写回上下文
          │
          └─▶ 判断任务已完成 ──▶ 输出最终答案
  ```

  - **思考(Thought)**:看当前状况,规划下一步该做什么;
  - **行动(Act)**:调用一个工具去执行——搜索、读写文件、跑代码、调 API 等;
  - **观察(Observe)**:把工具返回的真实结果写回上下文,作为下一轮思考的依据;
  - 然后回到思考,如此循环,直到模型判断任务完成、给出最终答案。
- 这就是 agent 与"一问一答"聊天的**本质区别**:它能拿到真实世界的反馈并据此修正——**工具报错也会作为一次"观察"进上下文,模型读到错误自己改参数重试**。
- 生产环境必须加护栏:最大轮数、token/成本预算、人工确认点,否则可能死循环烧钱。
- 为什么这两年被广泛认同:工具闭环让模型从"说"变成"做";每步有真实反馈、错误可观察可纠正,可靠性从"一次赌对错"变成"多轮收敛";任务有明确终态(测试通过、工单关闭)可评测;加上模型能力(长上下文、原生工具调用、指令遵循)跨过门槛,才从 demo 变成能用的生产系统。

</details>

### 5. 一个 SOP 的提示词要怎么写?

- Q1 有什么好用的工具?
- Q2 越长越好吗?

<details><summary>参考答案</summary>

- 结构五件套:角色与目标 / 输入说明 / 有序步骤(关键分支写"如果…则…") / 约束与输出格式(结构化输出) / 1–3 个 few-shot 示例覆盖边界 case。
- 工具:期望听到 **LangGPT**(Markdown 模板把提示词结构化,业务同事照模板填空);重点是框架带来可维护、可 review、可沉淀。
- **不是越长越好**:过长稀释注意力(Lost in the Middle)、约束互相打架;看的是有效约束密度,删掉后输出不变的句子都是噪音;要拿真实任务回归验证,不达标就拆任务/外置知识,不是继续堆字。

</details>

### 6. Skills 是什么?

- Q1 怎么编写?
- Q2 结构是什么?
- Q3 怎么测试?
- Q4 可一次触发多个吗?
- Q5 太多了会怎样?
- Q6 和以往代码/框架有什么区别?

<details><summary>参考答案</summary>

- 是什么:目录形态的能力包,**本质还是提示词**;核心机制是按需加载——启动只注入名称+描述当索引,命中才加载全文。
- 编写:可纯手写;期望听到 **skill-creator** 生成初稿再人工精修。功夫在 description(决定触发准确性)和确定性步骤下沉为脚本。
- 结构:SKILL.md(名称/描述/功能)+ 脚本目录 + 低频细节拆成小的功能划分 md。
- 测试:带/不带 skill 对照跑、每组多次;**skill-creator 支持 eval/方差基准测试**(多次跑取方差比质量);换新模型要回归、删掉已内化的指令。
- 可一次触发多个:可以,agent 已聪明到自主分工,不同环节用不同 skills,产物更专注。
- 太多的问题:描述索引占上下文、语义重叠误触发/漏触发、质量参差——需要命名规范与平台收口。
- 与代码/框架的区别:**编写和传播都没有门槛**——有想法、有能动性、有创意的人可以比其他人做得都好;代价是非确定性,确定性环节仍要下沉为代码。
- 🚩 **扣分项(错误回答)**:把 skills 说成"就是插件/就是 RAG";说不出任何一次改坏再改好的经历。

</details>

### 7. 怎么看 workflow 和 agent?

- Q1 怎么区分场景?
- Q2 可以融合吗?
- Q3 用过哪些产品?
- Q4 Dify 在企业中合适吗?

<details><summary>参考答案</summary>

- 区分核心问句:**任务路径事先能否穷举**。确定性流程用 workflow(可控、可审计、成本可预估);开放任务用 agent。原则:能用 workflow 解决的不上 agent。
- 可以融合:agent 内嵌固定流程(高风险环节固化成工具,只能调用不能绕过);workflow 节点挂 agent(需理解决策的节点交给 agent)。切分依据是出错代价。
- 产品:期望听到 Dify/Coze(n8n、LangGraph 也算),关键是有亲手搭建和踩坑,能说出至少一个产品的具体局限。
- Dify 是否合适是开放题,高分是分层结论:业务自助和原型验证用 Dify 类,核心生产链路代码化(agent SDK / LangGraph 自建)。
- 🚩 **扣分项(错误回答)**:张口站队"agent 万能"或"workflow 过时了"。

</details>

### 8. CLAUDE.md / AGENTS.md 是什么?

- Q1 怎么写?
- Q2 写多长?
- Q3 怎么保证更新?
- Q4 换模型注意什么?
- Q5 有什么最佳实践?

<details><summary>参考答案</summary>

- 每次会话自动注入上下文的长期指令文件——"给 AI 看的项目规矩":常用命令、规范、禁区;支持用户级/项目级/子目录级分层叠加。
- 怎么写:**短而硬**,只写确定性约束,不写背景教程;控制在几十行内,超了拆出去按需读;每条规则都应能追溯到一次真实翻车。
- 更新:用得不爽随手改、code review 带着改、定期清理失效条目——活文档。
- 换新模型要整体重审:老规则多是给老模型短板打的补丁,新模型可能已内化,留着反而过度约束。
- **追问 · 期望**:你的 CLAUDE.md 哪条规则救过你?新模型上线后删过哪条?——能讲具体规则+坑;从没删过=没真维护过

</details>

### 9. Hook 机制是什么?

- Q1 有哪些节点?
- Q2 能用来做什么?

<details><summary>参考答案</summary>

- 挂在 agent 生命周期节点上的回调,触发即必然执行——**确定性规则**,与概率性的提示词约定互补。分工:该强制的用 hook(拦截/审计/校验),需要判断力的交给模型。
- 节点:PreToolUse(可拦截)/ PostToolUse / UserPromptSubmit / Stop / SessionStart / SessionEnd;按"事前拦截/事后处理/会话级"三类讲清即可,不必背全。
- 用途:spec 增强、statusline 状态栏、发通知触发、触发硬件(红绿灯)——"无用但好玩"的例子恰是真玩过的强信号;平台侧放大为观测埋点、合规拦截、成本上报。
- **追问 · 期望**:全公司 runtime 要"危险命令一律禁止"怎么设计?——PreToolUse 统一拦截+平台下发规则,不靠各人提示词自觉

</details>

### 10. Spec 是什么?怎么用?有什么产物?

- Q1 用 superpowers 还是手搓?
- Q2 不同项目差异时如何用同一份 spec?
- Q3 spec 有什么缺点?

<details><summary>参考答案</summary>

- spec=动手前先产出结构化规格:需求/技术设计/任务拆解,落成 md 文档;人评审通过后 agent 按清单实现,跑偏回到文档改——产物可评审、可追溯。
- superpowers vs 手搓:现成方案流程完整上手快,但仪式重;手搓贴合团队、灵活,但要自己维护。合理答案是先用现成跑通再裁剪出轻量版,能说出裁掉了哪个环节。
- 项目差异:分层——通用流程层(步骤/文档结构/评审节点)做成模板或 skill 全团队统一;项目差异层(技术栈/规范)放各项目 CLAUDE.md,模板留引用位。
- 缺点:小任务不划算;spec 与代码会漂移(需"改代码先改 spec"约定或 hook 对账);想不清楚的需求写成文档还是想不清楚;替代不了 review 和测试。

</details>

### 11. Claude Code 和 Codex 有什么区别?

- Q1 模型有什么区别?
- Q2 更喜欢哪个?为什么?

<details><summary>参考答案</summary>

- 开放题,判卷重点是**是否双修**——两个都真实深用过,差异是亲手对比出来的,不是转述测评。

### 6. 怎么理解 openclaw 和 hermes-agent?

- Q1 运行机制/差异/带来了什么改变?
- Q2 什么是 Harness Engineering?
- Q3 ※为什么会有提示词工程→上下文工程→约束工程→循环工程的演变?※
- Q4 什么时候用 claude code,什么时候用它们?
- Q5 一定需要吗?
- Q6 可否用 Claude Code 替换 openclaw?

<details><summary>核验步骤与参考答案</summary>

- 核验:让候选人讲清两者机制差异 + 钉钉/飞书开放 API 的因果;亲手部署过的展示配置(加分,不强求)。
- openclaw:开源个人 AI 助理,常驻守护进程+本地 Gateway,接入微信/飞书/Telegram 等 20+ 渠道——"住在聊天软件里的全天候助理"。hermes-agent:Nous Research 出品,主打自我改进(从使用中沉淀技能、跨会话画像),可跑廉价 VPS。差异:前者重常驻+全渠道,后者重自学习+云端弹性。
- openclaw 的短板(能说明白=真用过):① **token 消耗远高于 Claude Code 且不透明**——常驻 + 全渠道轮询,账单难算;② **更新频繁但不稳定**,常有破坏式更新,历史功能说没就没。
- 带来的改变(判卷重点):个人 agent 爆发**倒逼平台开放**——钉钉/飞书把文档和私有 API 全开放、微信开放 agent 生态;对公司的含义是员工个人 agent 与企业系统的边界(数据安全/权限)成为新课题。
- **※演变原因(重点题)**:提示词工程=把单条指令说清楚;上下文工程=管理喂给模型的全部信息;约束工程(Harness)=用运行环境本身(权限/沙箱/工具边界/hook/观测)约束**单次** agent 运行;**循环工程(Loop Engineering,2026 最新一环)=工程化 agent 的持续运行**——设计一个自我驱动的循环:发现任务 → 派给 agent/子 agent → 验证结果 → 持久化状态 → 按调度或直到目标达成再决定下一步(对应 cc 的 /loop、定时任务、循环机制)。驱动力一路递进:**"说不清"(prompt)→"喂不对"(context)→"管不住"(harness)→"怎么让它自己持续转起来"(loop)**。追问:举一个靠提示词管不住、必须靠 harness 解决的例子。
- 分工:编码工程任务用 Claude Code;个人日常自动化、全渠道触达用 openclaw/hermes-agent;不互斥(后者可调度前者)。"一定需要吗"——不一定,按场景按需引入,能说出判断依据即可。
- **Q6 可否用 Claude Code 替换 openclaw?**——实际可以:cc 有定时任务 + /loop 循环机制(正是上面的循环工程),飞书/钉钉 cli 也开放了消息通道,把"常驻 + 定时 + 多渠道触达"几件事拼起来,cc 能覆盖 openclaw 的主要场景。判卷:能讲出"用 cc 的哪几样能力拼出 openclaw 的等价形态"即加分,而不是简单答"不能"。

</details>
